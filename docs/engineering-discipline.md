# 工程纪律（本轮沉淀）

> 三条都是**我自己踩过**的，写在这里是因为它们的共同点：
> **失败不是「报错」，而是「看起来是绿的」。**

---

## 1. 验证「这个失败是否我改之前就有」时，只读比对，绝不动工作区

**错误做法（我踩过）**：

```bash
git stash                                    # ❌ 会清掉我未提交的修复
git checkout <commit> -- <file>              # ❌ 会覆盖工作区文件
```

我用这两条去比对 e2e 基线，结果**把自己刚做完的 harness 修复覆盖掉了**，不得不重做一遍。

**正确做法**：

```bash
# 首选：拉一份干净的基线，全程不动主工作区
git worktree add /tmp/wrc-base <commit>
cd /tmp/wrc-base && npm run test:e2e        # 需要 node_modules 时：
                                                # cp -r <主仓>/node_modules ./node_modules
                                                # 或 npm ci
cd .. && git worktree remove --force /tmp/wrc-base

# 次选：只读取单个文件
git show <commit>:<path> > /tmp/x
diff /tmp/x <path>
```

> ★ 用 worktree 时注意：Windows 上 `/tmp` 会被解析成 `C:\tmp`，
>   `git worktree list` 显示的路径才是真身；`remove` 前先确认没有大目录残留
>   （`node_modules` 复制很慢，宁可先 `npm i --omit=optional` 或直接用主仓的软链）。

**判据本身也要给**：报告时要写清「哪几条、在哪个 commit、跑了几次」，
否则「基线也有」这句话无法被复核。

## 2. 测试不仅要验证「它能失败」，还要验证「它以正确的方式失败」

这一条我犯了两次，症状相同：**测试红了，但红的原因不是我以为的那个。**

### 案例 A：`new Function` 造的故障不是真实路径

我为了复现「`MorphDetail` 里 `addToStationProps` 作用域不成立」，
用 `new Function` 造了个看不到外层作用域的函数体。结果断言打到的是
**`new Function` 自己的 ReferenceError**，与 React 的渲染失败路径**不是同一条**。
测试红了，但红得毫无意义。

正确做法：**在探针里放一个真的不解构该 prop 的组件**，挂上真 React 渲染它 ——
断言打在真实的渲染失败上。

```jsx
// 探针里：真的少解构一个 prop
function MorphDetailBroken({ selectedIds }) {
  return <div>{Object.keys(addToStationProps).length}</div>  // ← ReferenceError
}
```

### 案例 B：替身模块没真的替换掉目标

esbuild 的 `onResolve` filter 写成 `/lib\/cloud\/stationWords\.js$/`，
而 `lib/addToStation.js` 里写的是 `'./cloud/stationWords.js'`（**不含** `lib/cloud/`）
→ 那次调用打到了**真模块**，而测试在断言 mock 的记录 —— 全绿，实际什么都没拦到。

**修法**：① 按**文件名**匹配（`/(^|\/)(stationWords|generate)\.js$/`）
② 打包后读产物做前置自检，断言「mock 的标记在、真模块的特征不在」。

### 两条附带的陷阱

- `const m = /re/` 拿到的是 **RegExp 对象**不是匹配结果，`Boolean(m)` 恒 `true`
  → 这条断言**永远绿**，且看起来完全正常。写完断言要问一句：「它有可能永远绿吗？」
- 断言「代码里没有某词」时**必须先剥注释** —— 解释性注释里提到该词是必要文档，
  不剥会逼人删掉正确说明。反过来，断言「只有一处 X」时也必须剥，否则会把
  注释里的讨论数成代码（我写「只有一处 `setRaw('')`」时数出 4 处就是这么来的）。

## 3. 凡「某组件用了新 prop」，必须渲染**那个组件**

`MorphDetail` 是 `App.jsx` 里的**顶层函数**（缩进 0），拿不到 `AppShell` 的变量。
我在它函数体里用了 `{...addToStationProps}` 却没在签名里解构
→ **右侧词群详情里勾选任意一个词就白屏**。

它逃过了三层：

| 检查 | 为什么没抓到 |
|---|---|
| `npm run build` | **esbuild 不做作用域分析** |
| 源码正则断言 | 只检查「`{...addToStationProps}` 这个**字符串**在不在」 |
| `test:cloud` | 那条断言是「匹配字符串」+ **单独 mount 被传的子组件** |

**修正后的规则**：
- 组件 A 用了新 prop ⇒ 测试要 **mount A**，不能只 mount A 内部的子组件；
- 「新增了一个 UI 状态」（比如某个按钮变 disabled）⇒ 断言**那个状态本身**，
  而不是它旁边的说明文字。我漏掉 C-04 的「不可点」就是这么漏的 ——
  我验了「下拉头有口径说明」，没验「那一项本身 disabled」。

## 4. 测试套件「静默吞掉后半段」比「失败」更危险

`qa-harness` 曾因一处文案变更导致 `byText(...)` 返回 `undefined`，
下一行 `.match()` 抛 TypeError → 整场中止 → **后面约 60 条断言一条没跑**，
而前面已经打出 30 条 PASS。**看起来是跑过了。**

**修法**（已实装）：

```js
class E2EContractBreak extends Error {}
function mustFind(sel, text, what) {
  const el = byText(sel, text)
  if (!el) {
    ok(false, `契约断裂：找不到${sel}「${text}」`)
    throw new E2EContractBreak(msg)   // 让 runner 明确区分「契约断裂」与「代码 bug」
  }
  return el
}
```

配套：runner 的 catch 要**在输出上就区分**这两者，并明说「后续用例**未执行**」——
否则读者只会看到一堆 PASS。

**通用形态**：凡是「后续要读它的属性」的查找，都要能判空并**显式失败**。
判空不能靠 `ok(false)` 然后继续往下跑（那样只是多一条红），
也不能靠抛裸异常（那样分不清是代码 bug 还是契约变了）。

## 5. 注释里的实测数字要写**最坏情况**，不是平均

我给缓存护栏写注释时，先填的是「单条约 26B、10 站满配 127KB」——
那是**按平均词形**算的。实测发现词形长度让单条体积差 **2.12 倍**：
`w.a` 是 17 B，`w.internationalization` 是 36 B。于是真实数字是：

| 档位 | 单条 | 10 站满配 | 护栏余量 |
|---|---|---|---|
| 短词 | 17 B | 83 KB | 68% |
| **长词** | **36 B** | **175.8 KB** | **31%** |

结论（「不调护栏」）在两端都成立，但**余量差了一倍多**。如果我只写平均值，
将来有人测护栏时会用短词得到「83KB，很安全」，而真实用户的长词场景已逼近上限。

**规则**：
- 写进注释/文档的体积数字，**取最坏情况**（最长词 / 最大行宽 / 最深嵌套）；
- 平均值可以作为补充，但**不能作为唯一给出的数**；
- 若最坏情况与平均差一个量级，必须把两档都列出来（像上表这样）。

## 6. 断言的「存在性」必须锚定区间

写裁剪测试时我踩了三次同一类错 —— 断言写成「全篇搜某个字符串」，
而**同样的内容在别处也出现**，于是注入缺陷后断言仍然全绿：

| 版本 | 写法 | 为什么假绿 |
|---|---|---|
| ① | `indexOf('setRefs(list')` | `setRefs(list.map(...))` **也包含**这个子串 |
| ② | `/17\s*B/.test(整段注释)` | 告诫段里又写了「（17B vs 36B）」 |
| ③ | `注释.slice(注释.indexOf('★ 体积'))` | 切片到**末尾**，告诫段仍在里面 |

修法：
- 要「必须是裸调用」→ 用**紧随其后的字符**锚定（`setRefs(list)` 的 `)`）；
- 要「某个小节里有 X」→ 切片**两端都锚定**（从 `★ 体积` 到 `★★ 调护栏之前`）；
- `\s*` 允许**零个**空白 ⇒ `17B` 也会被 `17\s*B` 匹配，
  所以「17 B」这种断言要写成 `/(^|[^.\d])17\s*B/`。

**一般形态**：**存在性断言必须限定位置，否则同样的内容在别处出现就会互相顶替。**
这与「剥注释」是同一条纪律的两个方向 —— 一个是别把注释当代码，一个是别让别处的
注释/代码替你顶包。

## 7. 「不是本轮引入的」不等于「不需要看」

我用 `git diff --quiet` 确认了某两条 e2e FAIL 依赖的四个组件**零改动**，
据此写下「属基线预存在、与本轮无关、先记待办」。

**这个结论是错的。** 修那两条断言的过程中，挖出**一个真的产品缺陷**：
语义关系连线（近义/反义）**一条都画不出来** —— `NetworkView` 传了带前缀的
图节点 id（`word:w.calm`）给 `relationsOf`，而后者要的是词条 id（`w.calm`）。

更关键的是它和断言问题的关系：
- 断言查 `svg line`，实现画 `path` ⇒ 断言**永远为假**；
- 于是「连线没画出来」这件事**没有任何测试在报警**；
- 断言与 bug 互相掩护，直到有人把断言改对，bug 才暴露。

**如果我当时满足于「这是既有问题、不在本轮范围」，这个 bug 就会一直留着。**

### 正确的排查顺序

1. 先问「这条断言在描述**什么产品行为**」
2. 再问「实现里到底有没有这个行为」
3. **最后**才问「是不是本轮引入的」

第 1 步就能发现「断言查的东西不存在」；第 2 步能发现被它掩盖的真 bug。
顺序颠倒就会停在「不是我的问题」这一步 —— 而且那句话听起来很合理。

### 归因判据的限度

`git diff --quiet` 能证明「**不是我们改坏的**」，不能证明「**它是对的**」。
这两件事之间差着一个「断言在描述什么」的问题，而那才是该先回答的。

## 8. 立「只靠人记得住的红线」时，必须同时评估能否机器化

`supabase/functions/generate-word/index.ts` 的文件头写着一条红线：
**service_role 不得用于「本应由 RLS 按 owner_id 保护」的写入**。

这条红线造成过两次真实事故：

| # | 形态 | 后果 |
|---|---|---|
| 1 | 写 `station_words` 用 service_role，`stations` 策略是 `owner_id = auth.uid()`（对 service_role 不生效），代码又不校验 stationId 归属 | 调用方可传**任意他人的 stationId**，把词条塞进别人的小站 |
| 2 | 用 service_role 调 `consume_generation_quota`（内部靠 `auth.uid()` 推导身份） | JWT 无 sub → `auth.uid()` 为 NULL → 抛异常；而错误分支被当成「无限制」⇒ 任何人可无限烧 DeepSeek 额度 |

两次都**修好了**。但修完之后，红线仍然只存在于注释里 ——
也就是说，它是一条「靠人记得住」的红线，而它的失效形态恰好是
**静默的越权**，评审时看不出来、测试也不会红。

### 纪律

**设计方立「只靠人记得住的红线」时，必须在同一份设计里说明：它能否机器化。
能，就写门禁；不能，说清为什么不能。** 不要把「我记得」当成控制手段。

### 判定规则必须基于**语义**，不是**写法**

这是机器化里最容易做错的一步。规则写成

- ❌ `if (code.includes('admin.from')) fail()` —— **过拟合到当前写法**。
  现在只有一个函数文件、一种写法；等有人把变量改名、把两行合并、
  或者合法地重构成 helper 函数，规则就误报。
- ✅ 「**用 service_role 客户端写 owner 保护表**」+「**写之前有没有归属校验**」

差别在于：前者匹配**代码形状**（变量名、语句排布），后者匹配**语义**
（这个客户端什么权限、这张表靠什么保护、这次写入有没有校验归属）。

**为什么这条必须死守**：`test:keys` 门禁上一轮就是被工程师自己推翻重做的 ——
它当时过拟合到当前实现，误报几次之后就没人再理它了。
而**误报比没有门禁更糟**：没人理的门禁等于没有门禁，
但它还会给人「已经有门禁了」的错觉。

配套的三条判据（`scripts/check-rls-writes.mjs` 是实现样例）：

1. **事实要从单一数据源解析，不要枚举**。
   本项目的 owner 列、外键、身份推导型 RPC 全部从
   `supabase/migrations/*.sql` 解析 —— 加表、改策略，门禁自动跟着变。
   写死表名必然在第二次改表时过期。
2. **判定依据要是「权限从哪来」，不是「变量叫什么」**。
   本门禁**溯源凭证**：`createClient` 的第二个参数追到哪个环境变量，
   决定它是 service_role 还是 anon。所以 `admin` / `sb` / `svc` /
   内联 `createClient(...)` 一视同仁 —— 改名绕不过去。
   推论：**溯源失败时要 fail closed**（按 service_role 处理）。
   代价是可能误报，收益是「换个写法藏起来」不再是漏洞。
3. **门禁必须内置正/反样本自检，且自检要能失败**。
   只跑真实文件的门禁无法证明「规则曾经命中过任何东西」。
   反样本要断言**具体命中项**（规则号 + 命中内容），不是「有违规就行」——
   否则规则退化成随便报一条也会绿。
   ⚠️ 参见本文 §2：`const m = /re/` 恒真那类坑，自检自己也会中招。

### 门禁的扫描范围要显式收窄

范围过宽 ⇒ 噪音 ⇒ 被绕过。本门禁只扫**服务端**代码
（`supabase/functions/**` + 其本地镜像 `scripts/dev-generate-plugin.mjs`），
**不扫** `scripts/qa-*.mjs` / `scripts/test-*.mjs`：
那些是测试夹具，用 service_role 造数据本来就是它们的本职工作。

### 顺带抓到的真 bug

门禁第一次跑就红了，报的是 `dev-generate-plugin.mjs`：
它用 service_role 写 `station_words` 且**从未校验 stationId 归属** ——
即第1 起事故，在 `index.ts` 里修了，**在它的本地镜像里没修**。
而红线二本来就写明「dev-generate-plugin.mjs 必须与本文件保持同构」。

这正是本文档第 7 条的形状：**断言/bug 互相掩护，只修一半最常见**。
如果没有机器检查，这份漂移会一直留着 —— 而它比原bug 更难发现，
因为「我明明修过了」。

> 附带一条元教训：镜像文件是红线类代码的**高危区**。
> 同一份逻辑存在两份拷贝时，机器门禁的价值不是「抓 bug」，
> 而是**抓「只修了一份」**。

## 9. 机器门禁的两个补充判据（立门禁时必须一起回答）

第 8 条讲的是「能不能机器化」。真做起来还有两问，比「规则怎么写」更该先回答。

### 9.1先问「能不能被绕过」，其次才是「好不好写」

我（设计方）最初提的方案是「把 service_role 客户端的构造收敛到一个命名的
`createServiceClient()` 出口，门禁只认这个出口」—— 理由是「这样门禁不用猜变量名」。
工程师驳回了，理由两条，我无法反驳：

1. **为了门禁去改生产代码**，代价不对等；
2. **它给绕过留了新路** —— 所有人都用同一个名字，改一处就全失效。

最终采用的方案是**凭证溯源**：追 `createClient` 的第二个参数追到哪个环境变量，
据此判 service/anon。**零侵入**，且实测证明不吃变量名那套
（把 `admin` 全量改名 `sb` 仍绿；再叠加删掉归属校验立刻红）。

> **一般形态：设计机器门禁时，判定规则优先考虑「能不能被绕过」，
> 其次才是「好不好写」。** 一个能被绕过的门禁，等于没有门禁还更坏 ——
> 它会给人虚假的安全感，而人不会去质疑一个「已经存在」的保护。

### 9.2 fail closed 之前，必须先测出它的**误报边界**

「凭证溯源失败就按service_role 处理」（fail closed）是有代价的：
**可能误报**。而误报的门禁会被绕过 —— 那就回到了 9.1 的问题。

所以 fail closed 不是「先这么写着，以后有空再测」，而是**必须先量出边界**。
实测结论（本项目）：

| 场景 | 溯源 | 结果 |
| --- | --- | --- |
| client 由函数入参传入 | ✗ 失败 | 曾误报 → 已修 |
| client 来自别的模块 | ✗ 失败 | 曾误报 → 已修 |
| key 由入参透传（dev 插件现状） | ✗ 失败 | 绿（靠豁免 A2） |
| key 是拼出来的 | ✗ 失败 | 绿（自限写入） |

误报的**根因**是：uid 溯源是**文件内**的，而豁免 A1要求 uid 可溯源到
`auth.getUser`。修法不是放宽A1，而是让**豁免 A2 命中即足以放行整个写入** ——
「写入前已确认父资源属于当前用户」本身就足以保证不越界，
比 A1（自限写入）是更强的保证，不该要求两者叠加。

> **一般形态：fail closed 之前先量误报边界；
> 若发现合法写法被误报，优先「补一个语义上更强的豁免」，
> 而不是「放宽判定」** —— 放宽判定等于给绕过开门。

这5 类误报边界已全部固化成门禁的正样本（12 条正样本里有 5 条就是它们），
所以以后有人改规则把它们改坏，门禁会立刻报出来。

## 10. 门禁要挂在**真实入口**上，而不是只挂在测试套件里

`test:rls` 一开始只并进了 `test:cloud`。但 `supabase/functions/**` 是**部署路径**：

| 入口 | 谁会走 | 挂了门禁吗 |
| --- | --- | --- |
| `npm run test:cloud` | 记得跑测试的人 | ✅ |
| `node scripts/deploy-generate-fn.mjs` | 改完函数直接部署的人 | ❌ **漏了** |

**漏了的那条才是真入口** —— 改完服务端代码直接部署的人，不一定会记得先跑测试套件。
只挂测试套件，等于门禁只保护「守规矩的人」。

已把 `test:rls` 接入 `deploy-generate-fn.mjs` 的预检（第 1b 步，exit 1 即 BLOCKED，
在任何写操作之前）。实测：注入越权后部署脚本 `BLOCKED` 并退出，不执行任何写命令。

> **一般形态：门禁的挂载点要和「事情真正发生的入口」对齐。
> 测试套件是开发者入口，部署脚本才是用户入口 —— 两边都要挂。**
> 推论：新增任何「会执行危险操作」的入口，都要问一遍「门禁在这里跑了吗」。

## 11. 「豁免」越强，越容易变成万能钥匙

`test:rls` 的豁免 A2（写入前已验父资源归属）为了让「uid 从入参传入」那类**合法**
写法不被误报，被我改成了「**A2 命中即足以放行整个写入**」。

那次改动是对的（A2 本来就是比 A1 更强的保证），但它有个我没看到的副作用：
**A2 变成了万能钥匙**。于是下面这个越权写法能白拿 A2 而被放行：

```js
const { data: owned } = await admin.from('stations')
  .select('id').eq('id', stationId).eq('owner_id', uid).maybeSingle()   // 前面合法
// …文件更早处或别的函数里有上面这段 …

export async function escalated(stationId, uid, wordKey) {   // 自己什么都不验
  await admin.from('station_words').upsert({ station_id: stationId, owner_id: body.owner_id, ... })
}
```

QA 用变异测试独立构造出来并复核成立。根因有两条：

| # | 根因 | 修法 |
| --- | --- | --- |
| 1 | A2 用 `code.slice(0, idx)` 找前置校验 —— **只看「文本上更靠前」**，不看函数边界 | 改为**函数边界切片**（`enclosingFunctionScope`） |
| 2 | A2 命中即放行整个写入 | A2 **只抵消「父表归属」那一项**；owner 列仍由 A1 独立判定 |

### 教训

**「豁免」不是豁免，是一条独立的判定。** 豁免越强，越容易变成万能钥匙 ——
它会从「这一项有保证」悄悄变成「整体都不用管」。

修的时候有个关键分寸：**不是把 A1 判据放宽，而是承认「归属校验已经证明过这个
表达式就是当前用户的 uid」**（A1②）。这样：

- 攻击者可控的值（`body.owner_id`）**不会**成为归属校验里被过滤的那个表达式，
  所以②不会给它开门；
- 而「uid 从入参传入」的合法写法仍然绿。

⇒ **优先补一个语义上更强、且攻击者无法伪造的判据来源，而不是放宽判据。**

### 附带的元教训：判据缺样本 = 可静默腐化

QA 还发现：A2 的「按 owner 列过滤」这条判据**没有任何自检样本** ——
把整条判据删掉，自检仍然全绿。而「全绿 ⇒ 规则可信」是这道门禁**唯一的**有效性论证。

已补 3 条反样本（只按主键查父表、跨函数白拿 A2、owner_id 取自请求体），
现在拆掉任一判据都会被自检抓住。**判据必须有对应样本，否则它随时可以腐化而不被发现。**

> 一个反面教材：我把 `selfScoped` 改名成 `ownerOk` 之后，
> QA 的 M8/M8b 变异目标（匹配旧变量名）就**悄悄失效**了 ——
> 变异脚本报「无效变异（模式没匹配上）」，看起来是 QA 的错，实际是我的重构
> 打掉了 A1 的变异覆盖。**重构改了变量名，要记得同步别人脚本里的变异目标。**
