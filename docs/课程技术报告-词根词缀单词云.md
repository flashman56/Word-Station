## 第一部分 · 这个项目整体在做什么

### 1.1 一句话概括

这是一个**帮助中国人背英语单词的网站**。它和普通背单词软件最大的不同是：**它是按"词根词缀"来组织单词的**。

什么是词根？英语里大量单词是可以拆开的，比如：

```
inspect  = in(向内) + spect(看)      →  "向内看" = 检查
respect  = re(再)   + spect(看)      →  "再看"   = 尊重
spectator= spect(看) + ator(人)      →  "看的人" = 观众
```

这三个词都围绕 `spect`（看）这个词根。学会一个词根，就顺带理解了一串单词——**这就是本项目的核心卖点**。

| 折叠后的"学习单元" | 54,811 |

## 第二部分 · 按模块拆解：用到了哪些专业知识

### 2.1 数据结构与算法

**① 哈希表（Hash Map）—— 全项目用得最多的数据结构**

> **术语：哈希表**。一种"用 key 直接找到 value"的数据结构，查找速度不随数据量增大而变慢（平均 O(1)）。
> 项目里的 `Map` 就是哈希表。

为什么必须用？因为词库有 6.4 万条。如果用数组一个个找（线性查找），查一个词平均要扫 3 万次；用哈希表查一次就到位。

典型用法：
- 词素表建索引：`src/hooks/useLearn.js` 里的 `morphById`（`new Map()` + `forEach`），供族键查找使用。
- 单词表建索引：`src/hooks/useLearn.js` 里的 `wordById`，让"按记录反查单词"不必重扫全表。
- 词族聚合：`src/lib/learning.js` 的 `buildLearnQueue` 用 `Map` 把同族词聚成一簇。

**② 排序的稳定性**

学习队列的排序规则是"词频升序 → 难度分升序 → 字母序"。最后一项**字母序**看似多余，其实很关键：它保证任何两个词的相对顺序都是确定的，不会出现"刷新一下顺序就变了"。
代码位置：`src/lib/learning.js` 的 `byForm` 比较函数。

**③ 分位数与单调回归（词汇量预测）**

词汇量估算不是简单数数。它按词频分档，统计每档"已掌握比例"，然后用一种叫 **PAVA（保序回归）** 的方法强制让"越冷门的词掌握率越低"这个常识成立，避免统计噪声导致曲线上下乱跳，最后外推出总词汇量。
> **术语：保序回归**。在保持"单调不增"约束的前提下拟合数据的方法。
> 代码位置：`src/lib/vocab.js` 的 `pavaNonIncreasing`（约 107 行）与 `estimateVocabulary`。

**④ 字符串归一化（stemming 的简化版）**

判断 `looks` 是否属于 `look`，以及校验构词拆解是否合法（各段拼起来要等于原词），都需要把字符串统一成同一形态（去大小写、去重音符号、去连字符）。
代码位置：`src/lib/derive.js`、`scripts/gen-loan-candidates.mjs` 里的 concat 校验。

### 2.2 面向对象与模块化思想

本项目**不是**传统"类与继承"式的面向对象，而是 React 生态主流的**组件化 + 函数式**风格。但背后的工程思想完全一致：

> **术语：封装（Encapsulation）**。把数据和操作数据的逻辑打包在一起，外部只通过明确定义的接口使用，不关心内部实现。

在项目中体现为：
- **组件封装**：`src/components/StudyCard.jsx` 只管"一张学习卡长什么样、点了会怎样"，不关心数据从哪来。
- **模块封装**：`src/lib/learning.js` 封装了所有学习调度规则，外界只调用 `buildLearnQueue`、`applyAnswer` 等函数。
- **纯函数派生层**：`src/lib/weakRoots.js` 是最典型的例子——它不依赖 React、不碰存储、不发网络请求，输入是数据、输出是数据。这样的代码最容易测试。

**项目里一条很重要的纪律**：`src/lib/learning.js`、`vocab.js`、`learnSync.js`、`syncLock.js`、`schema.js` 这几个文件被标记为**冻结文件**，从初始提交起不允许改动，新需求必须在它们**外层**实现。这是"接口稳定"思想的极端形式——越核心的模块越要少动。

### 2.3 网络通信

**① 动态 import（按需加载）**

> **术语：动态 import**。JavaScript 里 `import()` 写成函数调用形式时，代码不会在首屏全部下载，而是在执行到那一行时才去下载对应模块。

本项目词库压缩后约 3.5MB，如果首屏全下会很慢。做法是：
```js
// src/App.jsx（约 106 行）
const mod = await import('./data/words-entry.js')
```
配合构建工具的 `manualChunks` 配置，把词库切成独立文件：`vite.config.js` 的 `rollupOptions.output.manualChunks`。

**② 同源网关（绕过浏览器限制）**

浏览器里前端直连 Supabase 常被代理软件、广告拦截插件干扰。本项目让浏览器**只和自己域名通信**，再由服务端转发：
- 生产环境：`functions/_middleware.js`（Cloudflare Pages 的边缘函数），把 `/supabase/*` 转发到真正的 Supabase。
- 开发环境：`vite.config.js` 的 `server.proxy` 做同样的事。

> **术语：代理（Proxy）**。代替客户端去访问另一个服务器，再把结果转回来。

**③ 超时控制（AbortController）**

网络请求不能无限等。写小站时若 15 秒没响应就放弃并转入离线队列：
代码位置：`src/lib/cloud/stationWords.js`（约 60 行，`new AbortController()` + `setTimeout(..., 15000)`）。

### 2.4 数据库

用的是 **Supabase**（一个基于 PostgreSQL 的托管后端服务）。

> **术语：RLS（Row Level Security，行级安全）**。在数据库层面限制"某一行数据谁能看/谁能改"。即使前端代码被绕过，用户也读不到别人的数据。

项目里几张核心表：学习记录、小站、小站词条、私有词。权限判据统一是"这行的 ownerId 等于当前登录用户 id"。

一个很值得记住的实测经验（写进了项目记忆）：**越权读取不会报错，而是返回 200 + 空数组**。也就是说"没报错"不等于"权限正确"，测试时必须验证返回结果，不能只看有没有异常。

### 2.5 并发

> **术语：并发（Concurrency）**。多个任务在同一时间段内推进，可能交替执行。

项目里有三处典型并发：

**① 并发请求批量生成**：`scripts/gen-usage-extra.mjs` 用 `--concurrency 4~8` 控制同时向 DeepSeek 发几个请求。太快会被限流，太慢浪费时间。

**② 竞态防护（epoch 守卫）**：切换账号时，上一个账号未完成的异步请求可能晚一步返回，把数据写进新账号。项目在每个 `await` 之后检查"当前还是不是同一个 epoch"，不是就丢弃结果。
代码位置：`src/hooks/useLearnCloud.js`。

**③ 离线队列**：断网时操作不丢，先存草稿，联网后按序补传。区分"可重试"（网络问题）和"永久失败"（参数错误），前者保留重试、后者单独隔离，绝不无限重试。
代码位置：`src/lib/cloud/offline.js`。

### 2.6 缓存

这是本项目做得最细的一块，有三层：

**① 运行时三级缓存（音标/例句）**
内存 Map（最快） → IndexedDB（浏览器本地数据库，持久化） → 网络请求（最慢）。
代码位置：`src/lib/dict.js`（约 10-24 行）。

> **术语：IndexedDB**。浏览器内置的一个小型数据库，网页可以把结构化数据存在用户电脑上，关掉浏览器也不丢。

**② HTTP 缓存头**
`public/_headers` 文件定义每种资源的缓存策略：
- 带哈希的 JS/CSS：缓存 1 年且 `immutable`（因为内容变了文件名就会变，不可能拿到旧版）
- 字典分片：缓存 300 秒
- HTML 入口：每次回源校验（保证部署后用户立刻拿到新版）

> **踩过的坑（本项目真实教训）**：Cloudflare Pages 的 `_headers` **不是"最具体规则胜出"，而是把所有命中规则的 Cache-Control 拼在一起**。曾经写了 `/* no-cache` 兜底，导致字典分片的 `max-age=300` 被拼成 `...max-age=300, must-revalidate, no-cache`，而 HTTP 规范里 `no-cache` 会压过 `max-age`，缓存**完全失效却看起来配置正确**。修法是删掉通配兜底，只对具体路径声明。

**③ LLM 提示词缓存**
调用 DeepSeek 时，把固定的系统提示放在最前面，服务商会自动缓存这部分，重复部分按极低价格计费。

## 第三部分 · 完整技术报告

### 3.1 项目背景

中国人学英语的最大痛点是"单词记不住"。传统背单词软件按字母序或考纲顺序排列，单词之间是孤立的，只能死记。

语言学上更有效的方式是**词源记忆法**：英语中大量词汇来自拉丁语和希腊语，它们由有限的词根和词缀组合而成。掌握几百个词素，理论上可以理解上万个单词。

本项目的出发点就是：**用词素作为骨架重新组织整个词库**，让背单词从"记忆孤立符号"变成"理解构件组合"。

### 3.2 需求分析

**功能性需求**
1. 能浏览以词素为中心的单词网络
2. 能按词族成组学习（学完一族再进下一族）
3. 能记录学习进度并安排复习
4. 能自建词表（小站）
5. 能估算自己的词汇量
6. 能多设备同步（可选，游客可离线使用）

**非功能性需求**
1. **离线优先**：数据预先烘焙进构建产物，断网也能背
2. **首屏可接受**：词库很大，不能一次全塞进主包
3. **数据安全**：多账号之间绝对不能串数据
4. **数据正确性**：错的词源比没有词源更糟（这是本项目的最高红线）

### 3.3 系统设计

**数据分层**

```
原始词表（src/data/words-*.js）
        ↓  合并层（追加补丁）
合并后词表（src/data/words-entry.js 导出 words）
        ↓  折叠层（屈折归并）
学习单元（foldUnits）
        ↓  族键计算（defaultFamilyKeyOf）
词族分组（learnPool / weakRoots）
```

**关键设计决策**

1. **补丁合并而非修改原始数据**：`words-remorph.js` 和 `words-bookmorph.js` 是两层补丁，在返回前追加到词的 `morphs` 上（`src/data/words-entry.js` 第 72 行）。好处是原始数据永不被污染，补丁可随时重算。

2. **读时折叠而非写时删词**：屈折形式折叠只发生在"读"的时候，词库里一个词都不删——保留可查，只是不作为独立学习单元。

3. **纯派生优先**：新功能尽量"从已有数据算出来"，而不是新增存储字段。薄弱词根就是典型：不存任何新数据，全靠聚合已有记录。

### 3.4 技术选型

| 选择 | 备选方案 | 为什么选它 |
|---|---|---|
| React | Vue / 原生 | 生态最大，`useMemo` 便于做重计算缓存 |
| Vite | Webpack | 冷启动秒级，对 6 万词的巨型数据友好 |
| Supabase | 自建后端 / Firebase | 自带 PostgreSQL 与 RLS，省去写后端权限代码 |
| Cloudflare Pages | Vercel / 自购服务器 | 免费额度、全球 CDN、支持边缘函数做网关 |
| localStorage + IndexedDB | 纯云端 | 离线优先是硬需求 |
| DeepSeek | OpenAI / Claude | 批量生成场景便宜一个数量级 |

### 3.5 关键实现

**实现一：词族成组学习**

`defaultFamilyKeyOf`（`src/lib/learning.js` 约 240 行）取单词的第一个词根 id 作为族键；`buildLearnQueue` 按族聚簇。实测效果（用户验收时确认）：

```
3000~6000 档：management → manner → permanent → manual （全是 man- 族）
              → assignment → assigned （换到 assign 族）
```

> **重要澄清**：曾有一条评审意见认为"成组功能依赖云端，断网会失效"。经核查**不成立**——族键完全由打包进浏览器的本地数据算出，全程无任何网络调用。那条整改建议（把族键缓存到本地）实际上是要缓存一个本来就在本地的值。

**实现二：离线优先**

- 词库打进构建产物，首次加载后由浏览器缓存；
- 音标/例句走 IndexedDB 三级缓存（`src/lib/dict.js`）；
- 断网时的写操作进草稿队列（`src/lib/cloud/offline.js`），联网补传。

诚实说明边界：**本项目没有 Service Worker**，所以"断网后刷新页面"会失败，只有"已打开且不刷新"才能继续背。文案已按此如实修改（`src/App.jsx`）。

**实现三：新手队列质量（本轮最大改动）**

实测发现：折叠视图下，新手队列**前 1000 个词里只有 27.2% 有构词拆解**，其中 19.2% 是专有名词，而排在前面的具体是：

```
randy / harvey / ann / jonathan / dennis / dylan / eva / francisco
/ jess / jennifer / anthony / cooper / boston / ron / wednesday
/ batman / virginia / vince
```

**中文人名和地名占据了新手最宝贵的前几次学习会话**。这些词既不是学习目标，也没有词根可拆。

修复：把"排除专有名词"默认值从关改为开（`src/App.jsx`）。效果是有拆解词的比例 **27.2% → 33.7%**。

**实现四：我的薄弱词根（新增功能）**

把已有的三块数据（词族分组 × 学习记录 × 词素释义）串起来。

关键设计：`status === 'review'` **不能单独作为"薄弱"判据**。经核查它有 4 种来源，只有 1 种代表真的答错过：

| 来源 | 是否真答错 | 位置 |
|---|---|---|
| 答错 | ✅ 是 | `learning.js:155` |
| 手工加入待复习 | ❌ 否 | `learning.js:413` |
| 已掌握退回复习 | ❌ 否 | `learning.js:191` |
| 旧版数据迁移继承 | ❌ 否 | `migrate.js:479` |

所以判据定为 **`status === 'review'` 且 `incorrectCount > 0`**——后者只在真的答错时才增长，能自动排除后三类伪 review。
代码位置：`src/lib/weakRoots.js`。

**实现五：构建期磁盘泄漏修复**

`vite.config.js` 顶层静态引入了开发用的插件，而该插件依赖 Supabase 客户端。Vite 每次加载配置都会把配置和它的全部依赖打成一个临时文件，**每个约 121MB，每次构建新增 2 个**，累积 6 个后吃掉 727MB，把系统盘撑到可用 0 字节。

修复：插件改为仅开发模式动态引入（`await import(...)`）。修复后**构建期不再生成任何临时文件**。

### 3.6 难点与解决方案

| 难点 | 现象 | 解决 |
|---|---|---|
| 首屏体积 | 词库 14MB（gzip 3.5MB） | 数据切独立 chunk + 动态 import + 音标移出主包 |
| 多账号串数据 | 切号瞬间把 A 的记录写进 B | 三层防护：先换分区、epoch 守卫、等待在途请求收敛 |
| 缓存看似生效实则无效 | 配了 max-age 却仍每次回源 | 发现 Pages 会拼接规则，删掉 `/*` 通配兜底 |
| 磁盘被撑爆 | 构建报 ENOSPC、测试假红 | 定位到 121MB 临时文件，改动态引入根治 |
| 测试"连红" | 反复出现 flash 断言失败 | 原以为是时序问题，实为新功能每次扫 5.4 万词拖慢渲染 |
| 长期误判的 flake | flash 测试间歇失败 | 真因就是磁盘满，空间恢复后稳定通过 |

**其中最值得记住的一条**：薄弱词根功能导致 e2e 连续 3 次失败。没有把它当"已知抖动"放过去，而是查清了机制——`buildWeakRoots` 每次答题都要遍历 54,811 个学习单元，把 React 提交拖过 1.8 秒，于是那个 1800ms 自动消失的提示条在断言看到之前就没了。改为**只遍历学习记录**（几千条而非五万条）后恢复正常。这是真实的性能修复，不是放宽测试。

| 门禁 | 结果 |
|---|---|
| `npm run validate`（数据校验） | IS_PASS: YES，error 0 |
| `npm run test:e2e`（端到端） | 118 通过 / 0 失败 |
| `npm run test:cloud`（主链） | EXIT 0 |
| `npm run test:quality`（新增质量门槛） | IS_PASS: YES，自检 9/9 |

质量门槛还做了**变异测试**：往真实数据里注入 5 类缺陷，确认每条都能被正确拦截（而不是"恰好全绿"）。

### 3.8 总结与展望

**已完成的本轮优化**
1. 专有名词默认排除 —— 新手队列不再被英文人名占据
2. 我的薄弱词根 —— 按个人答错记录排序的差异化特性
3. 构建期磁盘泄漏根治 —— 121MB 临时文件归零
4. 缓存策略修正 —— 字典分片缓存真正生效
5. 数据质量门槛落地 —— 带自检与变异验证

**存在的真实局限（不粉饰）**
- 新手队列仍有约 66% 的词没有构词拆解，其中 mono（功能词如 the/and）确实无法拆解，但 loan 类里还有约 544 个高频词是可拆而没拆的
- 首屏 3.5MB（gzip）对移动网络仍偏重
- 没有 Service Worker，"断网刷新"仍会失败

**后续建议优先级**
1. **补全高频 loan 词拆解**（候选清单已产出，见 `reports/loan-decomp-candidates.md`，544 个里 108 个有依据，需人工审后入库）
2. **首屏按词频分片**（工程改造，但需先决定"统计是否只覆盖已加载词"这个口径问题）
3. 清理 21 条 1-2 字母的脏词条（`le` / `st` / `ad` 等排在全库前 6000，疑似切词错误）

**最重要的教训**

这个项目里最有价值的不是某个功能，而是几条反复被验证的工作纪律：
- **先测量再动手**。曾差点去补 186 个"折叠缺口"，量完才发现它们根本不在新手队列里——不测就做，等于用工作量代替价值。
- **评审意见要验证再采纳**。一条"成组功能依赖云端"的评审意见被证明是错的，照做会缓存一个本来就在本地的值。
- **测试变红不能靠改期望值变绿**。两处断言失败的真因是口径不一致（过滤后的 UI 数 vs 未过滤的存储数），修正的是基线口径而不是数字。
